## Plan 260427-l9m-01

### Context

Quick task `260427-kze` threaded `activeTx.evseId` from a Hasura query of `Transactions.evseId` into BPTSlider. That column is a **foreign key to the Evse table's primary key**, not the OCPP-level evse number. When the user ran a transaction against a station whose Evse row had `id ≠ evseTypeId`, `SetChargingProfile` failed with `Evse 1 not found`.

The correct field is `Evse.evseTypeId`, reachable in Hasura via the `Transactions.Evse` object relationship.

### Tasks

#### Task 1: Switch BPTSlider's evseId source to Evse.evseTypeId via the Hasura relation

- **files:**
  - `tools/citrineos-ui/src/api.js`
  - `tools/citrineos-ui/src/App.jsx`
- **action:**
  1. In `tools/citrineos-ui/src/api.js`, the `listTransactions` strict query currently selects `evseId` (line 55). Replace that single line with:
     ```graphql
     Evse { evseTypeId }
     ```
     Leave the fallback query (lines 69-78) unchanged — it does not select evseId at all and will continue to work as a defensive degradation path. The strict query is the only path that needs the relation.
  2. In `tools/citrineos-ui/src/App.jsx` (line 157), change:
     ```jsx
     evseId={activeTx.evseId}
     ```
     to:
     ```jsx
     evseId={activeTx.Evse?.evseTypeId}
     ```
- **verify:** `git diff` on those two files shows exactly two changed regions (one in api.js, one in App.jsx). No other files modified. BPTSlider.jsx is untouched.
- **done:** Both edits applied, atomic commit created on the current branch with the plan id in the message.

### Out of scope

- BPTSlider.jsx is correct as written: it accepts `evseId` and falls back to `1`. The `?? 1` fallback now triggers only when the transaction has no associated Evse row (e.g., transient state before TransactionEventRequest links it), which is the same fallback semantics the previous task established.
- The fallback query in api.js stays selectorless for evseId — adding the relation there would mean the fallback no longer "degrades gracefully" if Evse permissions change.
- StartTransactionModal's `useState(1)` default is intentional (user-editable) and out of scope (same as 260427-kze).
